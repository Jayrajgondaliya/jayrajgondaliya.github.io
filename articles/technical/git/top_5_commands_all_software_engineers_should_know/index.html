5 Git Commands All Software engineers Should Know

Starting with one of my favorite

1. Interactive staging: Stage Only What You Want#

Imagine, You’re working on a bug in app.py. To debug, you sprinkled temporary print statements all over the code. You finally fix the bug, and now you want to commit your changes.

But there’s a problem: if you do:

git add app.py
git commit -m "Fix bug in login function"

Git will stage everything, including your debug prints. You don’t want those cluttering the commit.

Normally, you’d have to manually remove all the debug lines, commit, and then re-add them if needed. Painful.

Welcome to the interactive staging:

git add -p app.py

Git now shows your changes in small “hunks” and asks what to do with each one:

y — stage this hunk (the bug fix)
n — skip this hunk (the debug prints)
s — split the hunk into smaller pieces
q — quit staging

Suddenly, you can stage only the bug fix, leaving all debug lines in your working directory. When you commit, your history is clean, and your debug prints stay intact for further testing.

Tip: Interactive staging is a lifesaver when working on multiple tasks in the same file. It keeps your commits focused, clean, and review-friendly.

2. Amend the Last Commit: Fix Mistakes Without Creating a New Commit#

Imagine you just committed a change:

git commit -m "Fix login bug"

Later, you realize: The commit message had a typo Or you forgot to include a critical file (forgotten_file.txt) in that commit.

Normally, you might think: “Oh no, I’ll have to create another commit to fix this.”

Luckily, Git has a solution: git commit --amend

git commit --amend -m "Corrected commit message"

This replaces the previous commit with a new one that has the corrected message. The changes in the commit remain intact—no need to redo your work.

Forgot a file? No problem! Add the forgotten file:

git add forgotten_file.txt
git commit --amend # Will ask to modify last message
or
git commit --amend --no-edit # --no-edit - keeps the original commit message.

The forgotten file is now included in the last commit.

Why it matters: Amending commits is incredibly useful when you want to keep your commit history clean, especially before pushing to a shared repository. It avoids cluttering history with “fixup” commits.

💡 Tip: Only amend commits that haven’t been pushed yet. Amending pushed commits can rewrite history and cause problems for others working on the branch.

⚠️ Warning: If you want to amend pushed commits, you need to use forced push

3. Travel Back in Your Git History: Reset to a Specific Date/Time#

Can you travel back in history and fix your mistakes?

It turns out, you can!

Imagine you’ve been working on a feature for hours, making multiple commits. Suddenly, you realize that the last few commits were mistakes or experimental changes. You want to rewind your repository to how it looked at a particular moment — say 2 PM on Jan 22, 2026.

Git makes this surprisingly easy with git log and git reset.

Approach 1: Using git log and git reset#

git log --before="2026-01-22 14:00"
git reset --hard <commit-hash>
git log --before shows all commits before the specified time.

Find the commit hash and use git reset --hard to reset HEAD, index, and working directory.

Approach 2: Resetting HEAD to a specific time#

You can reset your repository to a past state directly with:

# HEAD@{<timestamp>} refers to where HEAD was at a given time according to the reflog.
# Full date time
git reset --hard "HEAD@{2026-01-22 14:00}" 

# Date only (defaults to midnight)
git reset --hard "HEAD@{2026-01-22}"

# Relative time
git reset --hard "HEAD@{20 minutes ago}"

# Words / natural language
git reset --hard "HEAD@{yesterday}"
git reset --hard "HEAD@{2 days ago}"

You can also do branch@{<timestamp>} → Use this to reset other branches to a specific time.

4. Undo Multiple Commits Without Losing Changes#

Imagine you’ve been working on a feature and committed too early, maybe three times in a row. You realize that you:

  • Need to fix commit messages, or
  • Want to combine commits into one clean commit for history

You don’t want to lose your changes — just undo the commits.

Undo the last 3 commits#

git reset --soft HEAD~3 # Keep changes staged

or

git reset --mixed HEAD~3
# --mixed - the default if no flag is specified, keeps changes in
# your working directory but unstaged.

Gives you more control if you want to selectively stage changes again.

Why it matters Undoing commits without losing changes is useful when:

  • You committed too early with incomplete work.
  • You want to clean up commit history before pushing.
  • You need to combine multiple small commits into one meaningful commit.

💡 Tip: Always check git log before doing a reset to ensure you’re undoing the correct commits.

5. Stash Specific Files: Save Work Without Affecting Everything#

Imagine you’re working on a new feature in your project.

You have:

  • A partially completed login feature
  • Some unrelated changes in another file for experimental testing

You need to switch branches to fix a critical bug, but you don’t want to stash everything — only the files related to the login feature.

Here, Stashing specified files comes into picture.

Stash only specific files#

# git stash push -m "<message for stash>" <file1> <file2>
# Stash only login-related files
git stash push -m "WIP login feature" app/login.py app/utils.py

# Stash All
# Without message
git stash

# With a message
git stash push -m "WIP for new feature"

# including untracked files
git stash push -u -m "Include untracked files"

Why it matters Stashing specific files is useful when:

  • You’re working on multiple tasks simultaneously.
  • You want to temporarily save work on one task without affecting other ongoing changes.
  • You need to quickly switch branches without committing unfinished work.

💡 Tip: After switching branches, you can reapply your stash using:

git stash apply stash@{0}

# or drop it after you’re done:

git stash drop stash@{0}
